# Fiche projet — Velmo 2.0

> Chemin : `01_vitrine/Velmo2` · Stack : Python 3.11, LangChain (`ChatOpenAI` sur endpoint Azure AI Foundry `/openai/v1`), PostgreSQL + pgvector, Streamlit, FastAPI (webhooks OVH SMS / Twilio WhatsApp), LangSmith, uv, ruff, pytest · Taille : ~200 fichiers / ~4,3k LOC Python applicatif (src + apps + scripts + mlops) + 30 fichiers de tests

## 1. Objectif et contexte
Agent de support client e-commerce (fictif) avec trois exigences de « produit » : mémoire persistante (court + long terme, RGPD), garde-fous d'entrée/sortie, et boucle qualité mesurée qui bloque la livraison sous un seuil. Utilisateurs : clients finaux via web (Streamlit), SMS et WhatsApp, identité canonique partagée entre canaux (`customer_ref`). Statut : abouti pour un projet d'exercice (déployé sur Azure App Service, 57 cas d'éval, note 95/100), avec dette visible sur la sécurité des outils métier et des webhooks.

## 2. Architecture agentique
- Type : agent unique outillé (tool-calling) encadré par un pipeline déterministe + 2 LLM auxiliaires (classifieur de sécurité, « Judge » d'extraction de faits).
- Boucle d'exécution et orchestration : `VelmoAgent.process_message` enchaîne en code fixe garde-fou d'entrée → contexte mémoire → boucle tool-calling bornée à 3 itérations → garde-fou de sortie → persistance → Judge tous les 5 tours. Aucun superviseur LLM : l'ordre est codé en dur.
- Outils : 2 outils LangChain en lecture seule (`lookup_order`, `get_customer_orders`) qui renvoient du texte formaté et ne lèvent jamais ; identité injectée côté serveur via un dict module (`set_business_identity`).
- État et mémoire : court terme = fenêtre glissante 30 messages (RAM ou table Postgres avec TTL 48 h, partagée entre canaux) ; long terme = table `facts` (JSONB + embedding pgvector, versionnée sur 3 versions, soft-delete RGPD, `audit_log`, `extraction_metadata`) ; journal `guardrail_log`.

```mermaid
flowchart LR
  U[Web / SMS / WhatsApp] --> IG[Règles regex] --> CL[Classifieur LLM<br/>fail-safe BLOCK]
  CL --> MEM[Contexte: 30 msgs + facts]
  MEM --> LLM[LLM + outils<br/>max 3 itérations]
  LLM --> OG[Regex PII sortie] --> ST[Stockage court terme]
  ST -->|tour % 5| J[Judge -> facts pgvector]
```

## 3. Prompts et gestion du contexte
- Prompt système principal minimal, en anglais, construit par concaténation de chaînes dans l'orchestrateur ; faits long terme et historique court terme sont aplatis en texte dans le `SystemMessage` ([agent.py:109](../Velmo2/src/velmo/agent/agent.py:109), [agent.py:118](../Velmo2/src/velmo/agent/agent.py:118)).
- Classifieur : prompt fermé à 5 catégories, sortie d'un seul mot, `temperature=0`, `max_tokens=16`, catégorie inconnue rabattue sur `out_of_scope` ([classifier.py:11](../Velmo2/src/velmo/guardrails/classifier.py:11), [classifier.py:50](../Velmo2/src/velmo/guardrails/classifier.py:50)).
- Judge : prompt JSON avec schéma en clair, nettoyage manuel des fences Markdown puis validation Pydantic `FactData` (`confidence` borné 0..1), seuil de confiance 0,8 avant persistance ([judge.py:97](../Velmo2/src/velmo/memory/judge.py:97), [schema.py:10](../Velmo2/src/velmo/memory/schema.py:10), [manager.py:139](../Velmo2/src/velmo/memory/manager.py:139)).
- Longueur : bornée par la fenêtre de 30 messages et `RESPONSEMAXTOKENS=512` ; pas de comptage de tokens ; le contexte long terme injecté est `inspect_memory` (tous les faits actifs) et non la recherche sémantique `retrieve_context`.

## 4. Fiabilité
- Déterminisme vs LLM : règles regex (injection, secrets, haine) avant le LLM ; garde-fou de sortie 100 % regex (carte, IBAN, mot de passe) ; ordre du pipeline, bornage des outils, déclenchement du Judge et oubli RGPD en code. Le LLM ne décide que de la réponse, de l'appel d'outils, de la classification et de l'extraction de faits.
- Gestion d'erreurs : fail-safe BLOCK si le classifieur échoue après 2 tentatives ; mémoire, Judge, audit et tracing en « best effort » (jamais bloquants) ; repli RAM si Postgres injoignable ; repli `invoke` simple si `bind_tools` non supporté ; message de repli si la boucle d'outils finit vide. Pas de timeout explicite sur les appels LLM.
- Évaluations : 3 suites JSONL (12 mémoire, 37 garde-fous, 8 qualité) agrégées par `mlops/run_eval.py` en note pondérée 40/40/20, seuil 70, historique JSONL horodaté avec SHA git, rapport Markdown ; démonstration de non-régression par configuration volontairement dégradée (README). Assertions par sous-chaîne, pas de LLM-as-judge.
- Tests : ~30 fichiers pytest ; LLM remplacés par des stubs scriptés (`StubToolLLM`, `MagicMock(spec=KimiClassifier)`) ; Postgres réel (pgvector) en CI ; fixture autouse qui force la mémoire RAM pour le déterminisme.
- Observabilité : wrapper `trace_run` LangSmith no-op si désactivé, `ContextVar` pour propager `user_id`, scores custom (latence, blocage, confiance du Judge) envoyés en feedback ; journaux Postgres `guardrail_log`, `audit_log`, `extraction_metadata`.

## 5. Industrialisation
- CI `ci.yml` à chaque push/PR : service Postgres pgvector, clés factices, init schéma, ruff, pytest (gratuit, mocké). `quality.yml` en `workflow_dispatch` : vraies clés via secret `VELMO2` écrit en `.env`, seed de la base, suites d'éval, upload du rapport même en cas d'échec.
- Docker : image Streamlit en 2 couches uv (`--frozen`, deps puis projet), venv dans le `PATH` ; `docker-compose.yml` limité à Postgres. Pas d'image pour le serveur de webhooks.
- Config/secrets : classe `Settings` maison sur variables d'environnement sans underscore (héritage d'un incident Azure Key Vault documenté) ; singleton figé à l'import. Pas de versioning explicite des prompts ni de canary/rollback.

## 7. ✅ Bonnes pratiques à reprendre
1. **Gate qualité chiffré et versionné** — trois suites d'éval agrégées en une note pondérée avec seuil, code retour 1 sous le seuil, historique JSONL lié au SHA git et rapport régénéré ; la régression est démontrée en dégradant la config. — preuve : [`run_eval.py:36`](../Velmo2/mlops/run_eval.py:36), [`run_eval.py:82`](../Velmo2/mlops/run_eval.py:82), [`run_eval.py:205`](../Velmo2/mlops/run_eval.py:205), [`README.md:14`](../Velmo2/README.md:14)
2. **Garde-fou en deux étages, fail-safe BLOCK** — regex déterministes d'abord (gratuites, sans LLM), classifieur LLM ensuite ; si le classifieur tombe, on bloque au lieu de laisser passer. — preuve : [`input_guard.py:15`](../Velmo2/src/velmo/guardrails/input_guard.py:15), [`input_guard.py:27`](../Velmo2/src/velmo/guardrails/input_guard.py:27)
3. **Boucle d'outils bornée et testée** — `MAX_TOOL_ITERS = 3`, erreurs d'outil renvoyées au LLM comme texte, repli sur un message fixe, et un test qui vérifie qu'un LLM qui demande toujours un outil s'arrête. — preuve : [`agent.py:13`](../Velmo2/src/velmo/agent/agent.py:13), [`agent.py:49`](../Velmo2/src/velmo/agent/agent.py:49), [`test_agent_tool_loop.py:48`](../Velmo2/tests/test_agent_tool_loop.py:48)
4. **Classifieur à sortie fermée** — liste de catégories, `temperature=0`, `max_tokens=16`, valeur hors liste rabattue sur une catégorie bloquante, retries puis exception explicite. — preuve : [`classifier.py:9`](../Velmo2/src/velmo/guardrails/classifier.py:9), [`classifier.py:34`](../Velmo2/src/velmo/guardrails/classifier.py:34), [`classifier.py:50`](../Velmo2/src/velmo/guardrails/classifier.py:50)
5. **Mémoire longue gouvernée** — faits avec score de confiance filtré à 0,8, mise à jour versionnée (3 dernières versions), soft-delete RGPD et journal d'audit à chaque modification. — preuve : [`manager.py:139`](../Velmo2/src/velmo/memory/manager.py:139), [`long_term.py:102`](../Velmo2/src/velmo/memory/long_term.py:102), [`long_term.py:234`](../Velmo2/src/velmo/memory/long_term.py:234)
6. **Oubli RGPD multi-signaux** — un fait est ciblé par sa clé, sa valeur citée ou le contexte d'origine du message, pour compenser les clés mal choisies par le Judge ; couvert par des tests dédiés. — preuve : [`manager.py:202`](../Velmo2/src/velmo/memory/manager.py:202), [`test_memory_forget_rgpd.py:34`](../Velmo2/tests/test_memory_forget_rgpd.py:34)
7. **Dégradation gracieuse de la mémoire** — backend Postgres essayé puis repli RAM ; échecs de contexte, de stockage et du Judge n'empêchent jamais la réponse. — preuve : [`manager.py:62`](../Velmo2/src/velmo/memory/manager.py:62), [`agent.py:103`](../Velmo2/src/velmo/agent/agent.py:103), [`agent.py:188`](../Velmo2/src/velmo/agent/agent.py:188)
8. **Tracing non invasif et no-op par défaut** — `trace_run` fournit la `config` LangChain, propage `user_id` via `ContextVar` et pousse des scores métier en feedback ; tout échec de tracing est avalé. — preuve : [`tracing.py:1`](../Velmo2/src/velmo/observability/tracing.py:1), [`tracing.py:126`](../Velmo2/src/velmo/observability/tracing.py:126)
9. **Séparation CI gratuite / CI payante** — `ci.yml` mocké à chaque push avec vrai Postgres pgvector ; `quality.yml` sur vrai LLM déclenché à la main, rapport uploadé même en échec. — preuve : [`ci.yml:12`](../Velmo2/.github/workflows/ci.yml:12), [`quality.yml:13`](../Velmo2/.github/workflows/quality.yml:13), [`quality.yml:57`](../Velmo2/.github/workflows/quality.yml:57)
10. **Webhooks à accusé immédiat + déduplication** — réponse 200 avant l'appel LLM, traitement en `BackgroundTasks`, déduplication par id pour neutraliser les retries des fournisseurs ; signature Twilio vérifiée avec correction `X-Forwarded-Proto`. — preuve : [`main.py:34`](../Velmo2/apps/sms_server/main.py:34), [`main.py:104`](../Velmo2/apps/sms_server/main.py:104), [`main.py:157`](../Velmo2/apps/sms_server/main.py:157)
11. **Injection de dépendances pour tester sans réseau** — `VelmoAgent(settings, classifier, llm)` accepte des fakes ; stubs scriptés de LLM ; fixture autouse qui neutralise l'état Postgres persistant. — preuve : [`agent.py:24`](../Velmo2/src/velmo/agent/agent.py:24), [`test_agent_tool_loop.py:6`](../Velmo2/tests/test_agent_tool_loop.py:6), [`conftest.py:7`](../Velmo2/tests/conftest.py:7)
12. **Écriture d'audit qui ne bloque pas et DDL conditionnel** — `write_log` ne lève jamais ; l'`ALTER TABLE` n'est lancé que si nécessaire pour éviter un verrou exclusif (leçon d'incident documentée). — preuve : [`audit.py:27`](../Velmo2/src/velmo/guardrails/audit.py:27), [`audit.py:57`](../Velmo2/src/velmo/guardrails/audit.py:57)

## 8. ❌ Anti-patterns / limites observées
1. **Outils métier sans contrôle de propriété (IDOR)** — `lookup_order` lit n'importe quelle commande par numéro et `get_customer_orders` accepte n'importe quel email fourni par l'utilisateur ; le repository ne filtre pas par client. — conséquence : un utilisateur peut obtenir commandes, articles et suivi d'un autre client, en contradiction avec l'isolation soignée de la mémoire. — preuve : [`tools.py:50`](../Velmo2/src/velmo/business/tools.py:50), [`tools.py:72`](../Velmo2/src/velmo/business/tools.py:72), [`repository.py:30`](../Velmo2/src/velmo/business/repository.py:30)
2. **Webhook SMS non authentifié** — le webhook OVH n'a aucune vérification de signature (contrairement à Twilio) et l'identité est déduite du champ `senderid` du payload. — conséquence : n'importe qui peut usurper le numéro d'un client, et la payload brute (PII) est journalisée en INFO. — preuve : [`main.py:62`](../Velmo2/apps/sms_server/main.py:62), [`main.py:78`](../Velmo2/apps/sms_server/main.py:78)
3. **Tests garde-fous tautologiques** — le test « e2e » des 37 cas remplace le classifieur par un mock à mots-clés écrit pour matcher ces mêmes cas. — conséquence : 100 % vert sans rien prouver sur le vrai classifieur ; seule l'éval manuelle le mesure. — preuve : [`test_agent_e2e_guardrails.py:23`](../Velmo2/tests/test_agent_e2e_guardrails.py:23)
4. **L'éval mémoire ne teste pas l'agent réel** — `eval_memory` monte son propre prompt et son propre LLM avec recherche sémantique, alors que l'agent injecte tous les faits via `inspect_memory` ; elle force aussi l'extraction au lieu du déclencheur réel tous les 5 tours. — conséquence : la note mémoire 100 mesure un pipeline différent de la production. — preuve : [`eval_memory.py:41`](../Velmo2/scripts/eval_memory.py:41), [`eval_memory.py:136`](../Velmo2/scripts/eval_memory.py:136), [`agent.py:104`](../Velmo2/src/velmo/agent/agent.py:104)
5. **Assertions par sous-chaîne trop faibles et métriques estimées** — un cas qualité passe si la réponse contient « commande » ; le coût est dérivé de la latence (1 s ≈ 300 tokens) avec un tarif TODO. — conséquence : note qualité et coût affichés peu fiables. — preuve : [`eval_quality.py:59`](../Velmo2/scripts/eval_quality.py:59), [`run_eval.py:77`](../Velmo2/mlops/run_eval.py:77), [`quality_cases.jsonl:1`](../Velmo2/eval/quality_cases.jsonl:1), [`run_eval.py:70`](../Velmo2/mlops/run_eval.py:70)
6. **Gate de livraison manuel** — le README affirme que la CI bloque sous 70/100, mais `quality.yml` n'est qu'en `workflow_dispatch` et `ci.yml` n'exécute pas les évals. — conséquence : une régression peut être fusionnée sans que le gate ne tourne. — preuve : [`README.md:14`](../Velmo2/README.md:14), [`quality.yml:13`](../Velmo2/.github/workflows/quality.yml:13)
7. **Embedding factice silencieux** — si l'API d'embedding échoue, un vecteur aléatoire seedé par la somme des codes caractères est stocké sans signalement. — conséquence : recherche sémantique corrompue de façon invisible et durable en base. — preuve : [`long_term.py:46`](../Velmo2/src/velmo/memory/long_term.py:46)
8. **État global mutable par requête** — identité des outils dans un dict module et ensembles de déduplication en mémoire non bornés, justifiés par un « single-thread » non garanti par FastAPI/`BackgroundTasks`. — conséquence : fuite d'identité possible entre requêtes concurrentes, croissance mémoire, dédup perdue au redémarrage. — preuve : [`tools.py:10`](../Velmo2/src/velmo/business/tools.py:10), [`main.py:38`](../Velmo2/apps/sms_server/main.py:38)
9. **Config ignorée et Judge synchrone** — le Judge est déclenché par un `5` codé en dur (le paramètre `extraction_trigger_frequency` n'est jamais lu) et s'exécute dans le chemin de la requête. — conséquence : pic de latence tous les 5 tours, réglage illusoire. — preuve : [`agent.py:189`](../Velmo2/src/velmo/agent/agent.py:189), [`config.py:76`](../Velmo2/src/velmo/config.py:76)
10. **Détection d'oubli RGPD par sous-chaîne** — « supprime », « delete », « remove » n'importe où dans le message déclenchent la suppression, et le message complet est recopié dans la raison d'audit. — conséquence : faux positifs (« je veux supprimer un article du panier ») et donnée personnelle conservée dans le journal censé tracer son effacement. — preuve : [`manager.py:209`](../Velmo2/src/velmo/memory/manager.py:209), [`manager.py:246`](../Velmo2/src/velmo/memory/manager.py:246)
11. **Dérive documentaire et de nommage** — docstrings « DeepSeek », classe `KimiClassifier`, `.env.example` sur Kimi, README avec variables `AZURE_OPENAI_*` et Redis alors que le code lit `AZUREOPENAIAPIKEY` et que compose n'a pas de Redis. — conséquence : onboarding trompeur, mauvaise config au démarrage. — preuve : [`agent.py:1`](../Velmo2/src/velmo/agent/agent.py:1), [`README.md:41`](../Velmo2/README.md:41), [`README.md:53`](../Velmo2/README.md:53), [`config.py:13`](../Velmo2/src/velmo/config.py:13)
12. **Parsing JSON artisanal du Judge** — suppression manuelle des fences au lieu de `with_structured_output`. — conséquence : toute variante de format renvoie silencieusement zéro fait. — preuve : [`judge.py:97`](../Velmo2/src/velmo/memory/judge.py:97)
13. **Sortie PII trop large** — la regex carte bancaire (13 à 16 chiffres avec espaces) bloque la réponse entière plutôt que de la masquer. — conséquence : faux positifs sur numéros de suivi/SIRET et refus complet là où une rédaction suffirait. — preuve : [`rules.py:31`](../Velmo2/src/velmo/guardrails/rules.py:31), [`output_guard.py:5`](../Velmo2/src/velmo/guardrails/output_guard.py:5)

## 9. Idées originales / signatures du projet
- **Démonstration de non-régression par configuration sabotée** : même code, mémoire longue désactivée ou garde-fou retiré → la note tombe sous le seuil ; preuve chiffrée en tête de README.
- **Contexte d'origine stocké avec chaque fait** pour cibler l'oubli RGPD même quand le Judge a mal rangé la clé.
- **Mémoire court terme partagée entre canaux** (web, SMS, WhatsApp) via une identité canonique `customer_ref` et une table Postgres à TTL.
- **Persistance d'un identifiant découvert par un outil** (email trouvé par `get_customer_orders`) directement en fait long terme avec `source="tool_lookup"` ([agent.py:165](../Velmo2/src/velmo/agent/agent.py:165)).
- **Traçabilité du processus de dev agentique** : briefs, rapports et diffs de revue par tâche conservés dans `.superpowers/sdd/`, et post-mortem d'incident d'infra versionné dans `docs/`.
