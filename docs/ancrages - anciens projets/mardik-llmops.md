# Fiche projet — Mardik LLMOps (analyse de contrats v2)

> Chemin : `01_vitrine/Mardik deployement` (référence de travail : `02_en_cours/mardik-api-mlops`) · Stack : Python 3.12 (uv), FastAPI, Pydantic / pydantic-settings, httpx → Azure AI Inference (Kimi-K2.6) ou moteur factice déterministe, structlog, OpenTelemetry → Jaeger, pytest, ruff, mypy, Docker multi-étages, GitHub Actions → GHCR → Render · Taille : ~69 fichiers, ~2,7k LOC (≈ 1,1k LOC de `src/`, le reste en éval, tests, web et docs)

## 1. Objectif et contexte
Des juristes analysent des contrats commerciaux avec une v1 qui **tronque en silence à 8 000 caractères** et ne donne **aucun indice de fiabilité**. Le brief (« Plus jamais ça », après un déploiement manuel qui a coupé la production une demi-journée) impose de livrer une v2 sans jamais casser la v1 ni livrer à la main. La v2 lit le contrat entier et calcule un score de confiance. Elle passe par une chaîne gates bloquants → artefact étiqueté → canary piloté par métriques, avec trois boucles de rétroaction : rollback, promotion et enrichissement du jeu d'éval. Statut : **abouti en tant que démonstrateur LLMOps**. La qualité réelle du LLM n'est jamais mesurée : tout tourne sur le moteur factice, en CI comme sur Render ([render.yaml:43](<../Mardik deployement/render.yaml:43>)). Le `besoin_client.md` du brief n'a pas été fourni : les seuils sont des hypothèses écrites noir sur blanc ([besoin_client.md:3](<../Mardik deployement/besoin_client.md:3>)).

## 2. Architecture agentique
- Type : **pipeline LLM non agentique**, de type map → agrégation. Le contrat est découpé en segments de 6 000 caractères avec 400 de recouvrement. Chaque segment fait l'objet d'un appel LLM, puis le pipeline agrège les clauses (première occurrence retenue) et calcule un score composite ([v2.py:46](<../Mardik deployement/src/mardik/modele/v2.py:46>), [v2.py:59](<../Mardik deployement/src/mardik/modele/v2.py:59>)). La v1 est figée : un seul appel, sur le début du texte ([v1.py:22](<../Mardik deployement/src/mardik/modele/v1.py:22>)).
- Boucle et orchestration : une **passerelle canary applicative**. Elle tire au hasard v1 ou v2 selon `poids_v2` lu dans un fichier d'état ([canary.py:95](<../Mardik deployement/src/mardik/api/canary.py:95>)). Après chaque requête servie par la v2, l'ordre est fixe : écriture du signal, capture éventuelle, puis rollback ; la promotion n'est évaluée que si aucun rollback n'a eu lieu ([app.py:101](<../Mardik deployement/src/mardik/api/app.py:101>)). Le pilotage tient dans la boucle de requête : pas de superviseur ni de tâche de fond.
- Outils / contrats d'interface : une API HTTP (`/analyser` réparti, `/v1` et `/v2` forcés, `/sante`, `/api/signaux`, `/api/journal`, `/api/canary/*`, `/api/validation/*`). Le moteur LLM a un seul point d'entrée, `analyser_segment`, qui route vers le factice ou le distant ([llm.py:127](<../Mardik deployement/src/mardik/modele/llm.py:127>)). Pas d'outil LLM, pas de MCP.
- État et mémoire : uniquement des fichiers. `etat_canary.json` (poids, gel) ; `signaux.jsonl`, `journal.jsonl` et `file_validation.jsonl` en append ; `eval/golden.jsonl` et `reference_gate.json` ([config.py:20](<../Mardik deployement/src/mardik/config.py:20>)). Les accès sont protégés par des `threading.Lock` par module. Aucune mémoire conversationnelle.

```
client ─▶ /analyser ─▶ canary(poids) ─┬─ v1 : tronque 8k, 1 appel
                                       └─ v2 : segments ─▶ LLM ×N ─▶ score composite
                                              │
                    signaux.jsonl ◀───────────┘
                         │
          ┌── rollback (fenêtre 20) ──▶ poids=0 + gel ──┐
          ├── promotion (fenêtre 50, ≥ réf. gate) ──────┼─▶ journal.jsonl
          └── capture score<0,60 ─▶ pseudonymisation ─▶ relecture ─▶ golden.jsonl ─▶ gate CI
```

## 3. Prompts et gestion du contexte
- Le prompt tient dans une seule constante en dur. Il demande un JSON `{clauses, autoevaluation}`, avec `temperature: 0` et `response_format: json_object` ([llm.py:42](<../Mardik deployement/src/mardik/modele/llm.py:42>), [llm.py:87](<../Mardik deployement/src/mardik/modele/llm.py:87>)).
- La validation de sortie reste minimale. Le code filtre les clés hors des 5 clauses attendues et force `autoevaluation` en `float`, sans borne ni schéma ([llm.py:113](<../Mardik deployement/src/mardik/modele/llm.py:113>)). Il ne vérifie pas que la citation figure dans le texte.
- Longueur : la segmentation avec recouvrement évite qu'une clause coupée entre deux segments disparaisse. L'entrée est bornée à 150 000 caractères ; au-delà, l'API renvoie un 413 explicite ([app.py:60](<../Mardik deployement/src/mardik/api/app.py:60>)).
- Côté API, la sortie est structurée par Pydantic. `ReponseV2` hérite de `ReponseV1` et borne les scores avec `ge=0, le=1` ([schemas.py:37](<../Mardik deployement/src/mardik/api/schemas.py:37>)).
- **Écart avec la référence** : dans `mardik-api-mlops`, prompt, paramètres, `seed`, concurrence et **schéma JSON strict** (`additionalProperties: false`, `enum` de 14 types de clauses) forment un *bundle* YAML versionné ([config.yaml:15](../../02_en_cours/mardik-api-mlops/models/v2/config.yaml:15), [config.yaml:48](../../02_en_cours/mardik-api-mlops/models/v2/config.yaml:48)). La validation se fait clause par clause et rejette les clauses fautives sans casser l'analyse ([extraction.py:63](../../02_en_cours/mardik-api-mlops/app/pipeline/extraction.py:63)). La version aboutie a abandonné ce bundle et ce schéma.

## 4. Fiabilité
- Déterminisme vs LLM : 75 % du score est calculé dans le code : `0,40 × couverture + 0,35 × complétude + 0,25 × auto-évaluation` ([v2.py:22](<../Mardik deployement/src/mardik/modele/v2.py:22>)). Le code tranche toutes les décisions de pilotage (seuils, fenêtres, paliers) ; le LLM ne fournit que les extraits et une auto-évaluation.
- Erreurs : `ErreurMoteur` couvre timeout, HTTP et JSON invalide ([llm.py:108](<../Mardik deployement/src/mardik/modele/llm.py:108>)). L'API répond par des erreurs typées `{code, message, detail}`, avec un 503 `MOTEUR_INDISPONIBLE` ([app.py:160](<../Mardik deployement/src/mardik/api/app.py:160>)). Ni retry ni backoff. Dans la v2, un segment en échec est **ignoré** et fait baisser la couverture ([v2.py:70](<../Mardik deployement/src/mardik/modele/v2.py:70>)).
- Évaluations : le gate `eval/evaluer.py` calcule un F1 clauses attendues / trouvées, choisi pour qu'annoncer toutes les clauses ne paie pas ([evaluer.py:46](<../Mardik deployement/eval/evaluer.py:46>)). Il vérifie le seuil de 0,70 et une couverture ≥ 0,95, sort en code 1 en cas d'échec et alimente un historique et un rapport. Le jeu `golden.jsonl` compte **6 cas synthétiques** générés par `generer_golden.py`, auxquels s'ajoutent les cas de production validés. Ni LLM-as-judge ni éval sur le vrai modèle. La référence prévoyait `n_essais` et une dispersion de note ([run_eval.py:18](../../02_en_cours/mardik-api-mlops/eval/run_eval.py:18)) ; c'est abandonné.
- Tests : 16 tests. Les 10 critères du brief sont transcrits en tests d'acceptance, plus des tests de pseudonymisation. Les fichiers d'état sont isolés par fixture autouse ([conftest.py:24](<../Mardik deployement/tests/conftest.py:24>)). Le moteur factice remplace tout mock.
- Observabilité : `signaux.jsonl` couvre les cinq signaux imposés (latence, coût estimé via tokens, erreur, score, part v1/v2), tous estampillés avec l'`empreinte` ([signaux.py:23](<../Mardik deployement/src/mardik/observabilite/signaux.py:23>)). Le journal de pilotage enregistre signal, valeur, seuil, auteur et empreinte. S'y ajoutent un span OTel par requête, désactivable ([telemetrie.py:79](<../Mardik deployement/src/mardik/observabilite/telemetrie.py:79>)), un tableau de bord HTML et un histogramme des scores.

## 5. Industrialisation
- CI `llmops.yml` en trois jobs chaînés par `needs`. `gates` enchaîne ruff, mypy, pytest et l'éval, en moteur factice sans secret ([llmops.yml:35](<../Mardik deployement/.github/workflows/llmops.yml:35>)). `artefact` construit l'image, l'éprouve au démarrage et la publie sur GHCR. `deploiement` (environnement `production`) appelle le deploy hook Render avec le tag immuable, vérifie la version servie, puis applique un poids canary de 10 %.
- Docker multi-étages, utilisateur non privilégié, `HEALTHCHECK` sur `/sante`, volume `donnees` ([Dockerfile:17](<../Mardik deployement/Dockerfile:17>)). docker-compose ajoute Jaeger.
- Versioning : l'identité servie vaut code (`MARDIK_VERSION` = `<branche>-<sha7>`) + modèle + empreinte des seuils, condensés en `v-xxxxxxxx` ([config.py:114](<../Mardik deployement/src/mardik/config.py:114>)). Le prompt n'est versionné que par le commit.
- Rollback : automatique sur signal ou par bouton `/api/canary/rollback`, toujours via `canary.definir_poids` avec gel de la promotion. Il n'y a qu'une seule image : la v1 et la v2 cohabitent dans le même code, donc le rollback change le routage, pas l'artefact.
- Config et secrets : `pydantic-settings` + `.env` ignoré ; seul `.env.example` est versionné. Les secrets de déploiement sont optionnels : sans eux, la chaîne reste verte et l'affiche par un `::notice::` ([llmops.yml:197](<../Mardik deployement/.github/workflows/llmops.yml:197>)).
- Écart avec la référence : celle-ci avait un **registre local** (un dossier par version, `manifest.json` avec commit, empreinte et note d'éval, `index.json` actif/canary). Le rollback y repointait le bundle ([registry/__init__.py:1](../../02_en_cours/mardik-api-mlops/ops/registry/__init__.py:1)). Elle avait aussi un **proxy de dérive** entre l'app et le vrai fournisseur ([drift_proxy.py:1](../../02_en_cours/mardik-api-mlops/ops/drift_proxy.py:1)). La version aboutie remplace le premier par le tag d'image et le second par un simulateur de documents dégradés.

## 7. ✅ Bonnes pratiques à reprendre
1. **Gate bloquant par construction, pas par convention** — le job `artefact` déclare `needs: gates` ; si l'éval sort en code 1, l'image n'est jamais construite. Un test vérifie le code de sortie non nul — preuve : [llmops.yml:84](<../Mardik deployement/.github/workflows/llmops.yml:84>), [evaluer.py:184](<../Mardik deployement/eval/evaluer.py:184>), [test_acceptance_chaine.py:150](<../Mardik deployement/tests/test_acceptance_chaine.py:150>)
2. **Compatibilité ascendante garantie par la forme du contrat** — `ReponseV2(ReponseV1)` n'ajoute que des champs. Un test vérifie l'inclusion des champs et revalide la réponse v2 avec le schéma v1. Un client v1 « à ne jamais modifier » sert de témoin exécutable — preuve : [schemas.py:37](<../Mardik deployement/src/mardik/api/schemas.py:37>), [test_acceptance_chaine.py:77](<../Mardik deployement/tests/test_acceptance_chaine.py:77>), [client_v1.py:7](<../Mardik deployement/scripts/client_v1.py:7>)
3. **Identité de version = code + modèle + config** — l'empreinte des seuils de décision entre dans la version servie : déplacer un seuil change l'identité sans changer le commit. Chaque signal et chaque entrée de journal la portent, ce qui permet d'attribuer un comportement observé à une version précise — preuve : [config.py:98](<../Mardik deployement/src/mardik/config.py:98>), [config.py:114](<../Mardik deployement/src/mardik/config.py:114>), [test_acceptance_chaine.py:102](<../Mardik deployement/tests/test_acceptance_chaine.py:102>)
4. **Point unique de bascule, toujours tracé** — toute modification du trafic (rollback automatique, bouton, promotion, déploiement CI) passe par `definir_poids`. Cette fonction journalise signal, valeur observée, seuil, auteur, poids avant/après et gel — preuve : [canary.py:45](<../Mardik deployement/src/mardik/api/canary.py:45>), [journal.py:40](<../Mardik deployement/src/mardik/observabilite/journal.py:40>)
5. **Gates gratuits, déterministes et sans secret** — le moteur factice est un composant de production activé par variable d'environnement, pas un mock de test. L'éval et `traffic_sim` tournent donc hors pytest, sans clé, sur n'importe quelle PR — preuve : [llm.py:1](<../Mardik deployement/src/mardik/modele/llm.py:1>), [llmops.yml:38](<../Mardik deployement/.github/workflows/llmops.yml:38>), [dossier-de-conception.md:86](<../Mardik deployement/docs/dossier-de-conception.md:86>)
6. **Rollback sur la queue de distribution, pas sur la moyenne** — le déclencheur est la *part* d'analyses sous 0,60, au-delà de 25 % sur 20 requêtes v2. Une seule condition suffit, et la promotion est gelée ensuite pour éviter l'oscillation — preuve : [rollback.py:31](<../Mardik deployement/src/mardik/boucles/rollback.py:31>), [rollback.py:60](<../Mardik deployement/src/mardik/boucles/rollback.py:60>), [dossier-de-conception.md:331](<../Mardik deployement/docs/dossier-de-conception.md:331>)
7. **Promotion contre une référence figée au gate** — la v2 ne monte d'un palier que si son score moyen en production atteint celui mesuré par le gate, et non une moyenne glissante. Un refus est aussi une décision tracée (`promotion_refusee`) — preuve : [promotion.py:22](<../Mardik deployement/src/mardik/boucles/promotion.py:22>), [promotion.py:51](<../Mardik deployement/src/mardik/boucles/promotion.py:51>)
8. **Enrichissement du jeu d'éval avec humain dans la boucle et pseudonymisation avant disque** — un cas à faible confiance est pseudonymisé *avant* d'être écrit, puis relu par un juriste avant d'entrer dans `golden.jsonl`, qui est commité. La relecture joue un double rôle : vérifier l'exactitude et contrôler la confidentialité. Le décompte des substitutions suit le cas — preuve : [enrichissement.py:59](<../Mardik deployement/src/mardik/boucles/enrichissement.py:59>), [enrichissement.py:100](<../Mardik deployement/src/mardik/boucles/enrichissement.py:100>), [test_anonymisation.py:71](<../Mardik deployement/tests/test_anonymisation.py:71>)
9. **Image déployée par tag immuable et version servie vérifiée** — Render tire l'image GHCR `main-<sha7>` (`runtime: image`) au lieu de la reconstruire. La CI interroge ensuite `/sante` jusqu'à 10 minutes, jusqu'à lire la version attendue — preuve : [render.yaml:27](<../Mardik deployement/render.yaml:27>), [llmops.yml:202](<../Mardik deployement/.github/workflows/llmops.yml:202>), [llmops.yml:205](<../Mardik deployement/.github/workflows/llmops.yml:205>)
10. **Épreuve de démarrage avant publication** — le conteneur est lancé en CI. On vérifie que `/sante` répond avec l'étiquette injectée et qu'une requête invalide renvoie bien 422, avant tout push — preuve : [llmops.yml:113](<../Mardik deployement/.github/workflows/llmops.yml:113>)
11. **Seuils centralisés, sourcés et testés** — toutes les constantes chiffrées (taille max, rollback, paliers, fenêtres) vivent dans `Seuils`, avec un renvoi vers `besoin_client.md`. Le tableau de bord les expose — preuve : [config.py:35](<../Mardik deployement/src/mardik/config.py:35>), [app.py:223](<../Mardik deployement/src/mardik/api/app.py:223>)
12. **Une dérive simulée qui ne truque aucun score** — le profil `degrade` change la *distribution des entrées* (documents longs sans vocabulaire juridique). C'est donc l'observabilité réelle qui détecte la dérive — preuve : [traffic_sim.py:10](<../Mardik deployement/scripts/traffic_sim.py:10>), [dossier-de-conception.md:418](<../Mardik deployement/docs/dossier-de-conception.md:418>)
13. **Ordre signal → boucles explicite** — le signal de la requête courante est écrit avant que rollback et promotion relisent la fenêtre. Sans cela, la requête courante manquerait au diagnostic — preuve : [app.py:96](<../Mardik deployement/src/mardik/api/app.py:96>)

## 8. ❌ Anti-patterns / limites observées
1. **La fenêtre de promotion n'est pas remise à zéro par palier** — `promotion.evaluer` relit les 50 derniers signaux v2, sans filtre de date ni d'empreinte. Juste après un passage 10 → 50 %, la requête suivante voit encore 49 signaux « conformes » et repromeut à 100 %. Le même défaut vaut pour le rollback : après un dégel manuel, les 19 anciens mauvais signaux relancent un rollback immédiat. Conséquence : la règle « 50 requêtes par palier » du besoin client n'est pas respectée, et le test ne vérifie qu'un seul palier. La référence filtrait par fenêtre temporelle et par version (`store.lire(depuis_s=…, version=…)`) — preuve : [promotion.py:42](<../Mardik deployement/src/mardik/boucles/promotion.py:42>), [signaux.py:73](<../Mardik deployement/src/mardik/observabilite/signaux.py:73>), [test_acceptance_observabilite.py:73](<../Mardik deployement/tests/test_acceptance_observabilite.py:73>), [deploy.py:292](../../02_en_cours/mardik-api-mlops/ops/deploy.py:292)
2. **La v2 avale les pannes moteur, le signal « taux d'erreur » est mort** — `v2.analyser` attrape `ErreurMoteur` segment par segment et ne relève jamais d'exception. Si tous les segments échouent, le client reçoit un 200 avec des clauses vides et un score de 0. La branche 503 et `erreur=True` ne servent alors qu'à la v1. Conséquence : la condition de rollback « erreurs > 5 % » ne peut pas se déclencher pour la v2, et une panne fournisseur est déguisée en « faible confiance ». La référence distinguait panne du fournisseur (remontée en 503) et sortie hors schéma (clause écartée) — preuve : [v2.py:68](<../Mardik deployement/src/mardik/modele/v2.py:68>), [app.py:171](<../Mardik deployement/src/mardik/api/app.py:171>), [extraction.py:7](../../02_en_cours/mardik-api-mlops/app/pipeline/extraction.py:7)
3. **L'éval tourne en circuit fermé** — le vocabulaire du moteur factice est « aussi la définition opérationnelle de clause trouvée » du jeu d'éval, et les 6 cas sont composés à partir des mêmes blocs. F1 = 0,97 ne mesure donc que la chaîne, jamais un LLM. Le « workflow séparé déclenché à la main » pour le vrai modèle, annoncé dans le dossier, n'existe pas : seul `llmops.yml` est présent. Le Render de démo sert lui aussi le moteur factice — preuve : [llm.py:32](<../Mardik deployement/src/mardik/modele/llm.py:32>), [dernier.md:4](<../Mardik deployement/eval/rapports/dernier.md:4>), [dossier-de-conception.md:91](<../Mardik deployement/docs/dossier-de-conception.md:91>), [render.yaml:43](<../Mardik deployement/render.yaml:43>)
4. **La référence de promotion embarquée n'est pas celle du gate** — le gate écrit `reference_gate.json` dans le job `gates`. Le job `artefact` refait un checkout propre et `COPY eval/` embarque la version **commitée**, étiquetée `dev-local`. De plus, en vrai modèle, on comparerait un score de production LLM à une référence mesurée sur le moteur factice. Conséquence : le critère « score ≥ référence du gate » ne porte pas sur la version livrée — preuve : [llmops.yml:66](<../Mardik deployement/.github/workflows/llmops.yml:66>), [llmops.yml:94](<../Mardik deployement/.github/workflows/llmops.yml:94>), [Dockerfile:32](<../Mardik deployement/Dockerfile:32>), [reference_gate.json:2](<../Mardik deployement/eval/reference_gate.json:2>)
5. **« On ne reconstruit jamais ce qui a été testé », mais l'image est construite deux fois** — l'image éprouvée (`mardik:epreuve`, `load: true`) n'est pas celle publiée : un second `build-push-action` reconstruit l'image avec cache. Conséquence : rien ne garantit que l'artefact poussé est celui qui a passé l'épreuve. Il aurait fallu pousser l'image éprouvée ou épingler un digest — preuve : [llmops.yml:103](<../Mardik deployement/.github/workflows/llmops.yml:103>), [llmops.yml:146](<../Mardik deployement/.github/workflows/llmops.yml:146>), [README.md:89](<../Mardik deployement/README.md:89>)
6. **Le score de confiance récompense la présence, pas l'exactitude** — la couverture vaut 1 sauf en cas de panne, et la complétude augmente pour toute clause annoncée. En mode distant, aucune vérification ne contrôle que la citation figure dans le contrat. Conséquence : une hallucination *augmente* le score. La référence plafonnait la confiance déclarée par un **ancrage** de la citation dans le texte (`confiance_llm × (0,35 + 0,65 × ancrage)`) et pondérait le minimum dans le score global — preuve : [v2.py:81](<../Mardik deployement/src/mardik/modele/v2.py:81>), [llm.py:113](<../Mardik deployement/src/mardik/modele/llm.py:113>), [confiance.py:65](../../02_en_cours/mardik-api-mlops/app/pipeline/confiance.py:65)
7. **Endpoints de pilotage sans authentification, « auteur » déclaratif** — `/api/canary/poids`, `/rollback` et `/api/validation/{id}` sont ouverts. L'auteur est un champ libre (par défaut `operateur` ou `juriste`). Conséquence : n'importe qui peut basculer 100 % du trafic ou verser un cas dans `golden.jsonl`, et l'« auteur nominatif » du journal ne prouve rien. Le service de démo est public — preuve : [app.py:261](<../Mardik deployement/src/mardik/api/app.py:261>), [app.py:296](<../Mardik deployement/src/mardik/api/app.py:296>)
8. **Segments analysés en série, sans retry** — un contrat de 150 000 caractères fait environ 27 appels séquentiels, avec un timeout de 30 s chacun. Le p95 visé (≤ 20 s) est intenable avec un vrai LLM. La référence prévoyait `concurrence: 8` comme paramètre de version — preuve : [v2.py:67](<../Mardik deployement/src/mardik/modele/v2.py:67>), [config.py:71](<../Mardik deployement/src/mardik/config.py:71>), [config.yaml:39](../../02_en_cours/mardik-api-mlops/models/v2/config.yaml:39)
9. **État canary non atomique** — `definir_poids` lit l'état, puis écrit, sous deux verrous distincts : les deux opérations ne sont pas atomiques. Elle écrit aussi l'état *avant* le journal, alors que la doc affirme « écrit au journal avant de rendre la main ». Les verrous sont des `threading.Lock` sur fichiers locaux, donc invalides en multi-worker. Conséquence : course possible entre rollback et promotion simultanés, et bascule non tracée si l'écriture du journal échoue — preuve : [canary.py:62](<../Mardik deployement/src/mardik/api/canary.py:62>), [canary.py:71](<../Mardik deployement/src/mardik/api/canary.py:71>)
10. **Le journal est spammé par `promotion_refusee`** — la promotion est réévaluée à chaque requête v2. Une fois la fenêtre pleine et le score sous la référence, chaque requête ajoute une entrée de refus. Conséquence : l'audit est noyé et les lectures en O(n) se dégradent — preuve : [promotion.py:51](<../Mardik deployement/src/mardik/boucles/promotion.py:51>), [app.py:117](<../Mardik deployement/src/mardik/api/app.py:117>)
11. **Audit non persistant en démo** — sur Render gratuit, signaux, journal et état canary s'effacent à chaque redémarrage. C'est assumé dans le README, mais cela contredit la « valeur probante » revendiquée pour le journal — preuve : [README.md:118](<../Mardik deployement/README.md:118>)
